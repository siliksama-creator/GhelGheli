# ظرفیتِ خودکار: سرور ارتقا داده شد؟ خودش می‌فهمد

این سند می‌گوید چرا و چطور تعداد پروسه‌ها، تردپول، استخر دیتابیس و سقفِ
همزمانیِ پردازش عکس در این پروژه **از سخت‌افزار محاسبه می‌شود** و نه از یک
عددِ ثابت در کانفیگ. اگر روزی سرور را ارتقا دادید، هیچ‌چیز دستی لازم نیست.

---

## ۱. مشکلی که حل می‌کند

قبل از این کار، سه عدد سخت‌کد بودند:

| کجا | چه چیزی سخت‌کد بود | نتیجه |
|---|---|---|
| `ecosystem.config.cjs` | فهرستِ ثابتِ سه پروسه روی پورت‌های ۴۰۰۰/۴۰۰۱/۴۰۰۲ | ارتقای سرور هیچ اثری نداشت |
| هیچ‌جا | `UV_THREADPOOL_SIZE` (پیش‌فرضِ Node = ۴) | روی سرورهای بزرگ، گلوگاهِ پنهان |
| هیچ‌جا | سقفِ همزمانیِ پردازش عکس/مدل | یک موجِ آپلود، تأخیرِ کلِ API را بالا می‌برد |

اندازه‌گیریِ واقعی روی سرور (۱۸ عکسِ هم‌زمان): تأخیرِ API از ۳ms به **۲۹۱ms**
می‌رفت. یعنی آپلودِ ۱۸ نفر، دوئل و چتِ بقیه را کند می‌کرد.

---

## ۲. اعداد از کجا می‌آید

`backend/src/lib/capacity.js` تنها منبعِ حقیقت است. سخت‌افزار را می‌خواند
(`os.cpus()`, `os.totalmem()`)، **یک هسته را برای موتور بازیِ زنده و دیتابیس
کنار می‌گذارد** و بقیه را پخش می‌کند:

| هسته | گره کل (بازی+HTTP) | سقفِ پردازش عکس/مدل | تردپول | استخرِ DB هر پروسه |
|---|---|---|---|---|
| ۲ (امروز) | ۳ (۱+۲) | ۲ | ۴ | ۲۴ |
| ۴ | ۵ (۱+۴) | ۳ | ۸ | ۱۸ |
| ۸ | ۷ (۱+۶) | ۳ | ۱۲ | ۱۲ |

قاعده‌ها:

- **گره بازی همیشه یکی است.** موتور بازی (اتاق‌ها، صفِ حریف‌جویی، تایمرها)
  state زنده در حافظهٔ خودش دارد و در ۴۷ نقطه مستقیم به سوکتِ یک بازیکن
  `emit` می‌کند؛ دو گره سوکت یعنی دو بازیکن همدیگر را نمی‌بینند. شرح کامل در
  `docs/scaling-fa.md`.
- **یک هسته همیشه آزاد می‌ماند** تا دوئلِ زنده در لحظهٔ شلوغیِ آپلود لگ نزند.
- سقفِ پردازش عکس از اندازه‌گیری آمده، نه سلیقه: با ۱۲ عکسِ هم‌زمان،
  سقفِ ۲ هم ۲۶٪ سریع‌تر از ۱ بود و هم تأخیرِ API را روی ۳ms نگه می‌داشت
  (سقفِ ۴ تأخیرِ بقیه را به ۱۴ms و p95 را به ۶۱ms می‌برد).
- جمعِ استخرِ دیتابیسِ همهٔ پروسه‌ها زیر `max_connections=100` می‌ماند.
- سقفِ حافظهٔ هر پروسه از رمِ باقی‌مانده تقسیم می‌شود (بعد از کنار گذاشتنِ
  سهمِ چیزهای دیگرِ سرور مثل ربات حسابداری).

تنظیمِ دستی (اختیاری، برای شرایط خاص): `CAPACITY_HTTP`، `VISION_CONCURRENCY`،
`CAPACITY_UV`، `CAPACITY_RESERVE_MB`. و برای **آزمایش** روی ماشینِ دیگر:
`CAPACITY_FORCE_CORES=4`. (هرگز روی سرورِ واقعی نگذارید — تشخیصِ واقعی را
خاموش می‌کند.)

## ۳. پیکربندیِ خودکار (بدون دستِ انسان)

```
systemd timer (۰۴:۲۰ روزانه + ۹۰ ثانیه بعد از هر بوت)
        │
        ▼
/usr/local/bin/ghelgheli-capacity-apply.sh
        │  ۱) node backend/src/lib/capacity.js --json   ← سخت‌افزارِ واقعی
        │  ۲) مقایسه با backend/.capacity-state.json
        │  ۳) اگر عوض شده بود:
        │       • pm2 startOrReload (تعداد گره‌ها/تردپول/سقف‌ها)
        │       • انتظار تا سالم‌شدنِ پورت‌ها (health)
        │       • بازنویسیِ /etc/nginx/snippets/ghelgheli-upstream.conf
        │         + nginx -t + reload
        │       • به‌روزکردنِ لیستِ پورتِ اسکریپتِ سلامت
        │       • پیامِ تلگرام: از چه به چه تغییر کرد
        ▼
backend/.capacity-state.json   ← «این پروفایل کامل اعمال شده است»
```

نکاتِ ایمنی:

- اگر `nginx -t` رد شود، نسخهٔ قبلی **برگردانده** می‌شود و هیچ‌چیز عوض نمی‌شود.
- upstream فقط پورت‌هایی را می‌گیرد که واقعاً `/health` داده‌اند.
- اگر گرهٔ تازه بالا نیامد ولی گره‌های فعلی سالم‌اند، nginx دست‌نخورده
  می‌ماند و وضعیت ذخیره نمی‌شود (اجرای بعدی دوباره تلاش می‌کند).
- قفلِ `flock` مانعِ اجرای هم‌زمانِ دو نسخه می‌شود.
- تنزل هم مدیریت می‌شود: گره‌های اضافی از PM2 حذف می‌شوند.

## ۴. نصب

```bash
cd /var/www/GhelGheli
sudo bash scripts/capacity-install.sh --dry-run   # ببین چه می‌کند
sudo bash scripts/capacity-install.sh             # نصب + ثبتِ پروفایلِ فعلی
```

### بررسیِ وضعیت

```bash
/usr/local/bin/ghelgheli-capacity-apply.sh --dry-run   # تغییر لازم است یا نه
cat /var/www/GhelGheli/backend/.capacity-state.json    # پروفایلِ اعمال‌شده
curl -s http://127.0.0.1:4000/health | jq .capacity    # دیدِ خودِ پروسه
curl -s http://127.0.0.1:4000/health | jq .heavy       # صفِ پردازش عکس
tail -20 /var/log/ghelgheli-capacity.log               # تاریخچهٔ تغییرات
systemctl status ghelgheli-capacity.timer
```

`/health` برای درخواستِ **بیرونی** فقط `{ok, name}` برمی‌گرداند (تا شمارِ
هسته و بارِ سرور لو نرود)؛ جزئیات فقط برای درخواستِ داخلی/لوکال است.
`"ok":true` همیشه فیلدِ اول است چون دو اسکریپتِ مانیتورینگ با `grep` آن را
می‌خوانند.

## ۵. سقفِ هم‌زمانیِ پردازش عکس و مدل (`src/lib/heavy.js`)

پردازشِ آپلود و استنتاجِ مدل هر دو از یک دروازهٔ مشترک عبور می‌کنند:

- `imageService.optimizeUpload` (فشرده‌سازی + thumbnail‌ها)
- `serverVerify` → `embedCard` / `embedFace` / `cropVariants` (مسیرِ تشخیصِ سرور)

**دروازه فقط در حلقهٔ اصلی (والد) گرفته می‌شود.** مسیرِ تشخیص کار را به یک
`worker_thread` می‌سپارد؛ اگر داخلِ worker هم بشماریم، سقف دو برابر می‌شود.
پس والد «جا» را تا برگشتنِ جواب نگه می‌دارد و worker با `HEAVY_OFF=1` فقط
اجرا می‌کند. یک نگهبانِ `AsyncLocalStorage` هم جلوی قفل‌شدگیِ کارهای تودرتو
را می‌گیرد.

نتیجه: زیر موجِ آپلود، دوئل/چت/لاگین منابعِ آزاد دارند — همان هدفی که
اندازه‌گیری نشانش داد.

---

## ۶. پردازشِ عکس: یک decode به‌جای سه

`optimizeUpload` قبلاً سه بار مستقل فایل را decode می‌کرد (نسخهٔ اصلی + دو
thumbnail). حالا یک `sharp()` با `.clone()` سه خروجی می‌دهد:

| | قبل | بعد |
|---|---|---|
| decodeها | ۳ | ۱ |
| زمانِ عکسِ ۱۴۰۰px | ~۷۰۵ms (سرور) | ~۳۹۵ms |
| فایلِ ذخیره‌شده | — | **بایت‌به‌بایت مثل قبل** |

فایلِ اصلی (همان که کاربر می‌بیند و ذخیره می‌شود) با آزمونِ `sha256` تطبیق
داده شده؛ یعنی **کیفیت/محتوای عکس عوض نشده**. thumbnail‌ها حالا از پیکسلِ
خام ساخته می‌شوند (یک راندِ فشرده‌سازیِ کمتر) — ابعاد یکسان، کیفیت مساوی یا
کمی بهتر.

اثر روی **دقتِ تشخیص**: هیچ. اثر انگشتِ تصویر از بافرِ خامِ آپلود در همان
درخواست ساخته می‌شود (`photoCards.js` → `fpEngine.fingerprint(workBuf)`) و
مدلِ کارت هم ورودیِ ۲۲۴×۲۲۴ می‌بیند. یعنی نه فایلِ فشرده‌شده به مدل داده
می‌شود و نه بایت‌های فایل عوض شده. آزمون:
`node scripts/test-image-pipeline.js`

## ۷. چه چیزی هنوز خودکار نیست

- مسابقه‌های زنده هنوز تک‌گره‌اند (طبیعی — گام‌های ۲ تا ۴ در
  `docs/scaling-fa.md`).
- هشدارِ «صف بزرگ شد» به تلگرام وصل نشده؛ فعلاً عددِ صف در
  `/health` → `.heavy.queued` دیده می‌شود.
- ارتقای رمِ سرور فقط سقف‌های حافظه را عوض می‌کند؛ برای هستهٔ بیشتر همین
  مکانیزم گره‌های HTTP را اضافه می‌کند.
