# گزارش — ماموریت‌های اختصاصیِ چندتایی (چند کمپین هم‌زمان)

> خواستهٔ مالک: «باید یه کاری کنی که اگه ادمین خواست چند تا ماموریت اختصاصی بتونه قرار بده.»

قبل از این تغییر، ادمین فقط **یک** کارتِ ماموریت اختصاصی می‌توانست بگذارد.
حالا فهرستی از کارت‌ها می‌گذارد (پیش‌فرض ۵ تا) که همه بالای «ماموریت‌های
امروز» نشان داده می‌شوند — بدونِ آپدیتِ اپ.

## ۱) ادمین چه کاری می‌کند

| کار | جای پنل |
|---|---|
| افزودن کارتِ تازه | دکمهٔ «افزودن ماموریت» |
| جابه‌جاییِ ترتیب | فلشِ بالا/پایینِ هر کارت (ترتیب = ترتیبِ نمایش به کاربر) |
| روشن/خاموشِ هر کارت | کلیدِ «فعال باشد» داخلِ هر کارت |
| حذفِ کارت | دکمهٔ «حذف» (امتیازهای گرفته‌شده پاک نمی‌شود) |
| «دورهٔ تازه» | همان کارت با شناسهٔ نو: همه — حتی کسانی که گرفته‌اند — دوباره می‌توانند امتیاز بگیرند |
| شمارِ دریافت‌کنندگان | نشانِ «N دریافت» روی هر کارت (آمارِ زنده از دفترِ پیشرفت) |

ذخیره **اتمیک** است: کلِ فهرست با یک `PUT` می‌نشیند؛ یا همه یا هیچ‌کدام.

## ۲) قاعده‌ای که عوض نشد

- هر کاربر برای **هر ماموریت** یک‌بار امتیاز می‌گیرد؛ بعد آن کارت برای او
  پنهان می‌شود (خواستهٔ صریح مالک).
- امتیاز با منبعِ `mission` در دفترِ امتیاز می‌نشیند: «ماموریت اختصاصی: …».
- لینک فقط `http(s)`؛ متنِ خالیِ لینک ⇒ «اینجا کلیک کنید»؛ رنگ آبی/سبز.

## ۳) چیزهایی که عمداً نشکستند

- **اپِ نصب‌شده روی گوشیِ کاربران**: کلیدِ `custom` (تک‌ماموریتی) و مسیرِ
  `POST /api/missions/custom/claim` سرِ جایشان هستند، پس APKهای امروز یا
  کارتشان را از دست نمی‌دهند یا دکمهٔ دریافتشان نمی‌شکند. آن‌ها اولین
  ماموریتِ فعال را می‌بینند.
- **دادهٔ روی سرورِ زنده**: شکلِ قدیمیِ `app_settings.custom_mission` خوانده
  می‌شود و مثلِ فهرستِ تک‌عضوی دیده می‌شود — بدونِ مایگریشن.
- **ویرایشِ متن = همان دوره**: اصلاحِ غلطِ تایپی به همه امتیازِ تازه نمی‌دهد
  (شناسه دست‌نخورده می‌ماند). برای کمپینِ دوباره، «دورهٔ تازه» هست.

## ۴) قراردادها

```
app_settings.custom_mission = {
  items: [ { id, enabled, title, body, points,
             link: { url, text, color }, updatedAt, updatedBy } ],
  updatedAt, updatedBy
}

GET    /api/admin/custom-mission              → { missions, max, colors, preview, stats, … }
PUT    /api/admin/custom-mission              ← { items: [...] }        (شکلِ قدیمیِ تک‌ماموریتی هم پذیرفته می‌شود)
POST   /api/admin/custom-mission/:id/reset    → دورهٔ تازه با شناسهٔ نو
POST   /api/missions/custom/claim             → اولین ماموریتِ نگرفتهٔ کاربر  (کلاینتِ قدیمی)
POST   /api/missions/custom/:id/claim         → همان ماموریتِ خواسته‌شده    (کلاینتِ تازه)
GET    /api/missions , /api/growth/overview   → { custom, customMissions: [...] }
```

`customMissions` فقط کارت‌هایی را می‌دهد که **همین کاربر نگرفته** است.

## ۵) گاردها

- `backend/scripts/testMultiCustomMission.js` — ۵۳ بررسی: سازگاریِ دادهٔ
  قدیمی، ترتیب، شناسه‌ها، سقف، اعتبارسنجی، وضعیتِ هر کاربر، دریافتِ
  ماموریتِ مشخص، دورهٔ تازه، آمار، و سیم‌کشیِ **هر سه** کلاینت
  (وب `GrowthHub.jsx`، اندروید `growth_panel.dart`، پنل `custom-mission.jsx`).
- `testValidation.js` — همین گارد نسخهٔ اولِ مسیرِ `:id/reset` را گرفت چون
  `validateUuid` نداشت؛ حالا دارد.
- `reward-parity` (وب ↔ اندروید) — منبعِ «جشنِ دریافت» برای ماموریت‌های
  اختصاصی همان `custom` می‌ماند.

## ۶) تله‌ای که خوردیم و درسش

مسیرِ `:id` بدونِ `validateUuid` در `npm test` قرمز شد. اولین نسخه‌ای که
نوشتم، گاردِ `testValidation.js` (بندِ «هر مسیرِ :id اعتبارسنجی دارد») آن را
گرفت — یعنی گاردها همان‌جا که باید کار می‌کنند. اگر مسیرِ تازهٔ `:id` اضافه
می‌کنی، گاردِ شناسه را از یاد نبر.
