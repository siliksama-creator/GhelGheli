# سقفِ منابعِ Invoicle — چرا و چطور

> دستورِ کاربر (۱۷ شهریور): «invoicle رو خیلی محدود کن».
> این سند می‌گوید چه اندازه‌گیری شد، چه سقفی گذاشته شد، و چطور برگردانده می‌شود.

## ۱) چرا

سرور **۲ هسته و ۳.۹ گیگ رم** دارد و دو محصول روی آن کار می‌کنند. Invoicle
پنج سرویسِ systemd دارد و **هیچ سقفِ منابعی نداشت**:

| سرویس | اوجِ مصرفِ رم (از زمانِ بوت) |
|---|---|
| `invoicle-bot` | ۲۱۵ مگابایت |
| `invoicle-web` | ۵۶ مگابایت |
| `invoicle-worker@render` | ۲۰۴ مگابایت |
| `invoicle-worker@maintenance` | ۲۰۹ مگابایت |
| `invoicle-worker@payments` | ۳۰۷ مگابایت |
| **جمعِ اوج‌ها** | **~۱ گیگابایت** (و هر لحظه می‌توانست بیشتر شود) |

هیچ سقفی نبود ⇒ هر شب ممکن بود قلقلی از رم و CPU بیرون بماند. سواپِ سرور هم
۸۷۲ مگابایت پر شده بود.

## ۲) چه کردیم

همهٔ پنج سرویس داخلِ یک **سینیِ مشترک** (`invoicle.slice`) رفتند و سقف‌ها روی
همان سینی گذاشته شد — نه روی هر سرویس جدا. چرا سینی: با پنج سقفِ جدا هیچ‌کس
«جمع» را کنترل نمی‌کند؛ هر پنج‌تا می‌توانند هم‌زمان به سقفِ خودشان برسند.

| تنظیم | مقدار | یعنی چه |
|---|---|---|
| `MemoryHigh` | **۶۰۰M** | از این بالا کرنل حافظه را پس می‌گیرد و تخصیصِ تازه کند می‌شود (سرویس زنده می‌مانَد) |
| `MemoryMax` | **۹۰۰M** | خطِ آخر؛ عبور = کشته‌شدنِ پروسهٔ همان سینی (نه کلِ سرور) |
| `MemorySwapMax` | **۲۵۶M** | نمی‌تواند با سواپ‌خواری دیسک را اشغال کند |
| `CPUQuota` | **۸۰٪ یک هسته** | حداکثر ۴۰٪ توانِ کلِ ماشین، هر چند کار سنگین داشته باشد |
| `CPUWeight` | **۲۰** | در رقابت با قلقلی (وزن ۳۰۰) عقب می‌ماند |
| `IOWeight` | **۲۰** | فشارِ دیسکش کم‌وزن است |
| `TasksMax` | **۲۵۶** | سقفِ تعدادِ پروسه (ضدِ فورانِ پروسه) |

و سمتِ دیگرِ معادله — **قلقلی** روی `pm2-ghelgheli.service`:

`CPUWeight=300` · `IOWeight=300` · `MemoryLow=256M` (رمِ محافظت‌شدهٔ نرم؛ زیرِ
فشار، کرنل اول از Invoicle برمی‌دارد). سقفِ بالا برای قلقلی گذاشته نشد.

> نکتهٔ اجرایی: `Slice=` پس از `daemon-reload` فقط **تنظیم** است؛ پروسه‌های در
> حالِ اجرا تا **ری‌استارت** در cgroupِ قبلی می‌مانند. اجرای اولِ اسکریپت این
> تله را نشان داد (`invoicle.slice` خالی بود)؛ اسکریپت حالا جای واقعیِ پروسه را
> از `/proc/<pid>/cgroup` می‌خواند و اگر لازم باشد ری‌استارتِ چرخشی می‌کند.

## ۳) نتیجهٔ اندازه‌گیری‌شده (پس از اعمال)

| سنجه | قبل | بعد |
|---|---|---|
| مصرفِ واقعیِ Invoicle (anon در cgroup) | بدونِ سقف | **۵۷۴ مگابایت** (زیرِ سقفِ نرم) |
| رمِ آزادِ سرور | ~۱.۳ گیگ | **۲.۳ گیگ** |
| سواپِ مصرفی | ۸۷۲ مگابایت | **۳۲۰ مگابایت** |
| سرویس‌های Invoicle | active | **هر پنج‌تا active، صفر خطا** |
| قلقلی | ۳ گره سالم | **۳ گره سالم (`200`)** |

## ۴) سقفِ Invoicle چطور حسابِ رمِ قلقلی را هم عوض کرد

در `backend/src/lib/capacity.js` عددِ «رمِ کنارگذاشته» (`DEFAULT_RESERVE_MB`)
از **۱۸۰۰ → ۱۴۰۰** رفت، چون دیگر لازم نیست ۱.۸ گیگ برای Invoicle کنار بگذاریم:

```
MemTotal ۳۹۱۶ = Invoicle(سقفِ سخت ۹۰۰) + PostgreSQL(۴۰) + سیستم(۲۰۰) + اطمینان(۲۶۰) + قلقلی
```

اثرش روی همین سرور (۲ هسته، ۳ گره):

| | قبل | بعد |
|---|---|---|
| رمِ قابلِ استفادهٔ قلقلی | ۲۱۱۶ مگ | **۲۵۱۶ مگ** |
| `heapMB` هر گره | ۷۷۶ | **۹۲۲** |
| سقفِ ری‌استارتِ PM2 (RSS) | ۷۰۰ مگ | ۷۰۰ مگ (بی‌تغییر) |

سقفِ ری‌استارت عمداً بی‌تغییر ماند: اگر هر سه گره به سقفِ خودشان برسند
۳×۷۰۰=۲۱۰۰ مگ است که زیرِ ۲۵۱۶ مگِ بودجه می‌ماند ⇒ PM2 همیشه **قبل از**
OOM ری‌استارت می‌کند.

⚠️ اگر سقفِ Invoicle را بالا بردی (`MemoryMax=1200M`)، متغیرِ محیطی
`CAPACITY_RESERVE_MB` را هم بالا ببر (یا همین عددِ داخلِ `capacity.js` را).

## ۵) دستورها

```bash
# دیدنِ وضعیت (سرویس‌ها، سقف، مصرفِ واقعیِ سینی)
bash /usr/local/bin/invoicle-limit.sh --show

# اعمالِ دوباره (idempotent)
bash /usr/local/bin/invoicle-limit.sh

# بازگشتِ کامل به حالتِ قبل (حذفِ سقف‌ها و سینی)
bash /usr/local/bin/invoicle-limit.sh --rollback

# شل‌کردنِ سقفِ رم (نمونه: ۱.۲ گیگ)
sed -i 's/^MemoryMax=900M/MemoryMax=1200M/' /etc/systemd/system/invoicle.slice
systemctl daemon-reload
```

پشتیبانِ وضعیتِ پیش از تغییر: `/root/invoicle-limits-backup/state-*.txt`

## ۶) اگر روزی Invoicle خطا داد

نشانه: کارهای RQ در صف می‌مانند یا `oom-kill` داخلِ سینی در
`journalctl -u invoicle-worker@render` دیده می‌شود.

```bash
journalctl -u invoicle-worker@render --since "1 hour ago" | grep -i "oom\|killed"
```

درمان: `MemoryMax` را ۳۰۰ مگ بالا ببر (بندِ ۵). این سقف‌ها عمداً «خیلی محدود»
گذاشته شده‌اند؛ کمی گشادکردنشان یک دستور است.
