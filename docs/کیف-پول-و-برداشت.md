# کیف پول تومانی و سیستم برداشت

مستند فنی و عملیاتی. مخاطب: مدیر سیستم و توسعه‌دهندهٔ بعدی.

---

## ۱. تصویر کلی

کیف پول یک موجودی **تومانی** برای هر کاربر است که از چهار مسیر پر می‌شود و
از یک مسیر خالی می‌شود:

```
        ورودی‌ها                            خروجی
┌──────────────────────────┐         ┌──────────────────┐
│ کارت با جایزهٔ نقدی      │──┐      │                  │
│ گردونهٔ شانس (آماده)     │──┤      │  درخواست برداشت  │
│ جایزهٔ نقدی (بخش جوایز)  │──┼─► کیف ─►│  به کارت بانکی  │
│ جایزهٔ نقدی لیگ ماهانه   │──┤   پول │                  │
│ واریز دستی مدیر          │──┘      └──────────────────┘
└──────────────────────────┘
```

## ۲. چرا «دفتر کل» و نه فقط یک عدد؟

اگر فقط یک ستون `wallet_balance` داشتیم و آن را کم و زیاد می‌کردیم، اولین
باری که کاربری بگوید «پول من کم شده» هیچ راهی برای اثبات یا رد حرفش نبود.

پس دو چیز داریم:

| | نقش |
|---|---|
| `wallet_transactions` | **منبع حقیقت**. هر ریال یک ردیف دارد: جهت، مبلغ، منبع، مرجع، و موجودی دقیقاً بعد از آن تراکنش. هیچ ردیفی UPDATE یا DELETE نمی‌شود. |
| `users.wallet_balance` | فقط **کش** برای سرعت، با `CHECK (>= 0)` که حتی یک باگ در کد هم نتواند موجودی را منفی کند. |

هر لحظه باید این تساوی برقرار باشد:

```sql
SELECT u.id,
       u.wallet_balance,
       COALESCE(SUM(CASE WHEN t.direction='credit' THEN t.amount ELSE -t.amount END), 0) AS ledger
FROM users u
LEFT JOIN wallet_transactions t ON t.user_id = u.id
GROUP BY u.id, u.wallet_balance
HAVING u.wallet_balance <> COALESCE(SUM(CASE WHEN t.direction='credit' THEN t.amount ELSE -t.amount END), 0);
```

**اگر این کوئری حتی یک ردیف برگرداند، یعنی جایی اشکال هست.** بهتر است ماهانه
اجرا شود.

## ۳. محافظ‌های پولی

این‌ها مهم‌ترین بخش سیستم‌اند. هر کدام جلوی یک راه «گم شدن» یا «ساخته شدن»
پول را می‌گیرند:

| محافظ | چه فاجعه‌ای را جلوگیری می‌کند |
|---|---|
| `UNIQUE (source, reference_id)` | دو بار زدن «پرداخت شد» روی یک جایزه، مبلغ را دو بار واریز می‌کرد. حالا واریز دوم بی‌اثر است و `duplicate: true` برمی‌گرداند. |
| `SELECT ... FOR UPDATE` روی کاربر | دو تراکنش همزمان هر دو موجودی قدیمی را می‌خواندند و یکی بی‌صدا گم می‌شد (lost update). |
| `CHECK (wallet_balance >= 0)` | حتی `UPDATE` دستی در psql هم نمی‌تواند موجودی را منفی کند. |
| جدول گذار وضعیت | «رد کردن» دوبارهٔ یک درخواست، دو بار مبلغ را برمی‌گرداند — یعنی از هیچ پول می‌ساخت. |
| بلوکه‌کردن هنگام درخواست | کاربر با ۶۰٬۰۰۰ تومان نمی‌تواند دو درخواست ۵۰٬۰۰۰ تومانی ثبت کند. |
| اسنپ‌شات کارت | کاربر بعد از ثبت درخواست کارتش را عوض کند، پول همچنان به کارتی می‌رود که خودش تأیید کرده بود. |
| اجبار «دلیل» در واریز دستی | دفتر کل پر از تراکنش بی‌توضیح نمی‌شود. |
| `requireRole()` روی واریز دستی | فقط `super_admin`؛ این endpoint عملاً «چاپ پول» است. |

### گذارهای مجاز وضعیت برداشت

```
pending  ──► approved ──► paid      (پایان)
   │             │
   └──► rejected ◄┘                 (پایان، مبلغ برمی‌گردد)
   │
   └──► canceled (توسط خود کاربر)   (پایان، مبلغ برمی‌گردد)
```

هر گذار دیگری با خطای ۴۰۹ رد می‌شود.

## ۴. جریان برداشت از دید کاربر

1. کاربر وارد تب **کیف پول** می‌شود.
2. اگر کارت بانکی ندارد، دکمهٔ برداشت دلیلش را می‌گوید و میان‌بر «ثبت کارت» می‌دهد.
3. فرم کارت: شماره ۱۶ رقمی با اعتبارسنجی **زندهٔ** Luhn، نام صاحب کارت، شبای اختیاری. نام بانک به‌محض کامل شدن ۶ رقم اول نشان داده می‌شود.
4. کاربر مبلغ را وارد می‌کند (یا از چیپ‌های آماده انتخاب می‌کند). حداقل **۵۰٬۰۰۰ تومان**.
5. یک دیالوگ تأیید مبلغ، کارت مقصد و نام صاحب کارت را نشان می‌دهد.
6. با ثبت، مبلغ **بلافاصله بلوکه** می‌شود و در دفتر کل با منبع `withdrawal_hold` ثبت می‌گردد.
7. تا قبل از تأیید مدیر، کاربر می‌تواند خودش لغو کند و پول برگردد.

## ۵. جریان از دید مدیر (اپ اندروید)

پنل مدیر → تب **کیف پول**:

- **چهار کارت آمار**: در انتظار بررسی، تأییدشده (در صف واریز)، واریزشدهٔ ۳۰ روز اخیر، و **کل بدهی کیف پول‌ها** (مجموع موجودی همهٔ کاربران — عددی که باید همیشه بدانید).
- **فهرست درخواست‌ها** با فیلتر وضعیت و جست‌وجو بر اساس موبایل/نام/شماره کارت.
- هر کارت درخواست: مبلغ، مشخصات کاربر، موجودی فعلی‌اش، و **اطلاعات واریز**.
- شماره کارت، نام صاحب کارت و شبا با **یک لمس کپی** می‌شوند — تایپ دستی ۱۶ رقم رایج‌ترین راه واریز به حساب اشتباه است.
- سه اقدام: **تأیید** → **واریز کردم** (با کد پیگیری اختیاری) → یا **رد و برگشت وجه** (با دلیل که به کاربر نمایش داده می‌شود).
- **تنظیمات کیف پول**: فعال/غیرفعال بودن برداشت، حداقل و حداکثر مبلغ، حداکثر درخواست همزمان هر کاربر، و یادداشت نمایشی.

## ۶. تعریف کارت با جایزهٔ نقدی

پنل مدیر → **کارت و کد** → فیلد جدید «جایزهٔ نقدی (تومان)».

- صفر = کارت فقط امتیاز می‌دهد (رفتار قبلی، همهٔ کارت‌های موجود دست‌نخورده‌اند).
- بزرگ‌تر از صفر = هنگام ثبت کد توسط کاربر، مبلغ **در همان تراکنش** به کیف پولش واریز و یک نوتیفیکیشن ارسال می‌شود.

جوایز بخش «جوایز» هم فیلد «مبلغ واریز به کیف پول» گرفتند که فقط برای نوع
«نقدی» نمایش داده می‌شود. واریز هنگام علامت زدن **«پرداخت شد»** انجام می‌شود،
نه هنگام تأیید — تا مدیر بتواند اول تأیید کند و بعد در زمان مناسب پول را آزاد کند.

همین منطق برای **جایزهٔ لیگ** هم برقرار است: `league_payouts` وقتی `paid`
می‌شود، مبلغ به کیف پول می‌رود.

## ۷. اتصال گردونهٔ شانس (برای بعد)

عمداً endpoint عمومی نساختم. اگر مسیری مثل `POST /api/wheel/spin` وجود داشته
باشد که مبلغ را از **بدنهٔ درخواست** بگیرد، هر کاربری با یک `curl` می‌تواند
هر مبلغی برای خودش واریز کند.

وقتی منطق گردونه ساخته شد، باید مبلغ را **سمت سرور** از روی جدول جوایز گردونه
تعیین کند و بعد صدا بزند:

```js
await creditWheelPrize(userId, amount, spinId, 'جایزهٔ گردونه');
```

`spinId` مرجع یکتاست و تضمین می‌کند یک چرخش دو بار پول ندهد.

## ۸. حریم خصوصی شماره کارت

شمارهٔ کامل کارت **فقط** در یک نقطه از API خارج می‌شود:
`GET /api/admin/wallet/withdrawals` — پشت `adminAuth`، چون مدیر باید واقعاً
واریز کند.

همه‌جای دیگر ماسک‌شده است (`6037-••••-••••-0988`)، از جمله `/api/profile` که
هر بار باز شدن اپ فراخوانی می‌شود و در کش HTTP و گزارش‌های خطا می‌نشیند.
تابع `safeUser()` این کار را به‌صورت متمرکز انجام می‌دهد.

## ۹. مسیرهای API

### کاربر
| متد | مسیر | توضیح |
|---|---|---|
| GET | `/api/wallet` | موجودی، آمار، کارت ماسک‌شده، قوانین، دلیل مسدودی |
| GET | `/api/wallet/transactions` | دفتر تراکنش‌ها (صفحه‌بندی) |

| DELETE | `/api/wallet/bank-card` | حذف کارت |
| POST | `/api/wallet/withdrawals` | ثبت درخواست برداشت |
| GET | `/api/wallet/withdrawals` | فهرست درخواست‌های من |
| POST | `/api/wallet/withdrawals/:id/cancel` | لغو توسط کاربر |

| متد | مسیر | نقش |
|---|---|---|
| GET | `/api/admin/wallet/stats` | همه |

## ۱۰. استقرار

```bash
cd /var/www/GhelGheli
bash scripts/deploy.sh     # بکاپ → pull → migrate → build → reload → health-check
```

`scripts/deploy.sh` خودش قبل از هر کاری از دیتابیس بکاپ می‌گیرد و اگر
health-check شکست بخورد به کامیت قبلی برمی‌گردد.

مایگریشن `015_wallet.sql` **افزایشی و بی‌خطر** است: فقط ستون و جدول اضافه
می‌کند، هیچ دادهٔ موجودی را تغییر نمی‌دهد، و همهٔ ستون‌های جدید مقدار پیش‌فرض
دارند. کارت‌ها و جوایز موجود با `cash_amount = 0` دقیقاً مثل قبل کار می‌کنند.
